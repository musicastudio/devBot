# devBot reference

devBot keeps the Discord bug-list and feature-list forums in step with the FSVR and FM8.plus GitHub issues. Each repo is a product with its own forum tag, and `REPOS` at the top of `bot.py` lists them.

## What it does

- Every open issue gets a forum post in bug-list or feature-list, tagged with product, category and importance. When the issue closes, devBot backs the thread up and deletes it from the forum. The backup holds every message and attached file, and is kept in `~/devbot/archive/` on legion. Reopening the issue opens a new thread that carries on from the backup.
- Every commit pushed to main is checked against the open issues of its repo, by its message and its diff, since a message can leave out what the code makes plain. A merged pull request or branch is checked once as a whole, with the messages of all the commits it brings and its diff against main, and its commits aren't checked again one by one. `glm-5.3-flash` links the commit to the issues it touches, and `glm-5.3` judges each of those twice with the whole issue, its comments and the commit. A close needs both confirmations, each with a sentence that really appears in the commit or its diff, so an issue reported after the commit, one waiting on its reporter, or one the commit only explains stays open. An issue filed from the Discord scan counts as reported on the date of its first Discord report. A confirmed close waits 30 minutes, which the thread shows, since the session that made the commit usually explains the fix and often closes the issue itself. A further commit resolving the same issue in that time joins the same close and restarts the 30 minutes. When the time is up, an issue someone already closed is left alone, one somebody commented on since the commit closes without a comment from devBot, and any other gets one comment listing the commits before it closes. Waiting closes are kept in `state.json`, so a restart doesn't lose them.
- A message posted in an issue's thread goes to the GitHub issue as a comment from devBot, quoted and credited to its author with a link back, and its files go with it the same way a report's do. Tags of @devBot or @claudeOpus are commands and stay in Discord, and so do bots' messages and Discord's own notices. A handover brief leaves these copies out, since it carries the whole thread anyway.
- Every open pull request gets a thread in the pull-requests forum, tagged with its product. The first post shows the branch, a link to the changes for review, the description and the approvals so far. A new thread starts with the comments already on the pull request, and from then on comments go both ways as they do in issue threads. GitHub's reviews and comments on the code come to the thread too. Anyone in the Team or Contributors role approves with `@devBot approve` in the thread, which also goes to GitHub as a comment, and at two approvals from different people devBot merges the pull request with a merge commit naming them. A pull request opened by someone on the team counts as their approval, so one more is enough. `GITHUB_TEAM` in `bot.py` lists the team's GitHub logins with their Discord accounts, and a pull request devBot opened for claudeOpus counts for whoever its branch is named after. devBot also names the people on that list by their GitHub login everywhere it writes, on GitHub and in Discord, and anyone else by their Discord name. Approvals hold for the branch's latest commit: a push starts them over, and the merge names that commit so GitHub refuses it if the branch moved. When GitHub won't merge, for a conflict say, devBot says why, and approving again retries. A merged or closed pull request's thread is backed up and deleted like a closed issue's.
- Pull requests and commits that name an issue number post a note in that issue's thread, or only in the activity log once the issue is closed. The model's other guesses go only to the activity log.
- devBot says what it does in #devbot: new threads, closes and reopens, Discord reports, pull requests, and each commit as "Pushed. Verifying…" edited to its outcome.
- Tagging @devBot in a reply to any message, with a link to a message, or with the report written after the tag, checks the report against open issues. A match adds the report to the existing thread, otherwise devBot files a GitHub issue and opens a thread for it. devBot always shows `glm-5.3` the last 25 messages before the tag, however old, and the report is written from the ones about the same problem along with the tag. So `@devBot make a feature request for the above` files the messages it points at, and `@devBot add the 12 kHz notch to the bug list` files the discussion of the notch above it, crediting whoever wrote those messages. Messages describing unrelated bugs or requests are filed as separate issues from a single tag, while a specific case of a broader request stays part of that request.
- Tagging @devBot with an open issue named, like `@devBot correct #92's 'full-mesh algorithm' to 'full-mesh custom algorithm'` or `@devBot update FSVR#91 with information from this post <link>`, or tagging it in an issue's thread, changes that issue. `glm-5.3` applies exactly the change asked for to the title and body, keeps quoted messages as written, credits what it adds from a message to its author, and rewrites a placeholder description from the message that supplies the real report. devBot then edits the GitHub issue, retags and renames the thread, comments on GitHub with who changed what, and posts the same note in the thread when the tag came from elsewhere. Files on the messages go to the issue like `add image`. A tag the model reads as a different report is filed as one instead.
- Images in a GitHub issue's body are attached to its thread's first post, which marks each with [image]. Each sync checks the open issues for images their threads don't have yet, so new issues, edits and reopened issues all get them.
- Images and files on a reported message go with it. devBot attaches them to the new thread and embeds them in the GitHub issue, and for a duplicate it adds them to the existing thread and the issue. GitHub's API can't attach files to issues and Discord's links expire, so devBot copies each file to a `devbot-files` branch in the repo and links it from there. That branch holds only those files.
- `@devBot add image` adds more files to an issue: the ones on your message, or on the message you reply to. Tagged in an issue's thread it adds them to that issue, and `@devBot add image FSVR#80` works anywhere. The files go into a GitHub comment, and into the thread when the command came from elsewhere.
- `@devBot close` closes an issue from Discord. Tagged in an issue's thread it closes that issue, and `@devBot close FSVR#49` closes the one named. In reply to a message saying something is fixed, devBot works out which issue it means and closes it once you react ✅. Closing needs permission to manage threads. When someone without it uses the command, devBot adds their message to the issue's thread for a maintainer to confirm. A close comments on the GitHub issue with who closed it and the Discord message, then the thread is backed up and deleted as usual.
- `@devBot delete` removes an issue filed in error from GitHub and Discord instead of closing it, in its thread or with the issue named, like `@devBot delete FSVR#81`. It needs permission to manage threads, asks for a ✅ first since it can't be undone, and keeps no backup. GitHub lets only repo admins delete issues, through its GraphQL API. An issue deleted on GitHub directly loses its thread at the next sync, since each sync checks the open issues devBot tracks against GitHub's list.
- Tagging @claudeOpus in an issue's thread hands the issue to the coding agent, and so does asking @devBot for work on an issue rather than a change to its text, like `@devBot in FSVR#95, read through the FS1R manual and note every parameter that depends on another`. devBot posts it with claudeOpus tagged, your note, and a brief attached: the GitHub issue, its comments and the whole Discord thread, with the thread's images. In #fsvr-development, #fsvr-gui or #fsvr-questions devBot opens a thread on your message, named for the issue, and posts there, so claudeOpus works under the request. From an issue's thread or any other channel the post goes to #scratchpad. claudeOpus doesn't read the forums, since it would answer a direct tag in an issue's thread as well as devBot's handover of it. claudeOpus starts its own thread from that post, and devBot tags the person who handed it over on the post and adds them to that thread. James, rgwan and anyone in the Team or Contributors role can hand work over, and claudeOpus takes messages from the same people. claudeOpus admits devBot's post through `DISCORD_ALLOW_BOTS` and a patch that limits it to devBot's ID, both in Disclaude's 1RFS folder.
- The musica.studio contact form sends each message to the private #contact-inbox channel too, through a webhook whose URL `contact.php` reads from `/var/www/private/devbot_webhook.txt` on the web server. The name and subject go with it, never the email address. `glm-5.3-flash` decides whether a message reports a bug or asks for a feature. A report goes through the same duplicate check as one from Discord: a match is added to that issue's thread, and anything new is filed as devBot with a thread. The issue body leaves out names, email addresses and phone numbers, since the issue is public. devBot marks each inbox message 🆕 filed, 🔁 matched or ➖ not a report. The email to James is unchanged.
- A command that has to wait, behind a sync's commit checks say, gets a ⏳ until it's answered. Every command is kept in `state.json` until devBot replies, so one a restart cuts off runs again when devBot starts. Approvals don't wait for the commit checks at all.
- Any message in #gh-events triggers a sync straight away, and the bot checks GitHub every five minutes regardless.
- The first run is the populate. It imports every open issue and records existing commits without announcing them.

`glm-5.3` can't see images, so before a report or an issue change `glm-5.3-flash` looks at every image on the messages involved and describes what it shows: controls, values, settings, labels and plotted data. `glm-5.3` gets those descriptions alongside the messages, and the quoted original report keeps only what people wrote. Audio files are passed on by name only.

Categories and importance levels are the lists at the top of `bot.py`, and the forum tags are created from them on startup. Both models run on Ollama Cloud. `glm-5.3-flash` classifies and takes the first look at each commit, and `glm-5.3` makes every call that closes an issue or merges a report into one.

## Running

devBot runs on legion@10.0.0.3 as a systemd user service from `~/devbot`. Run only one copy, since a second instance with its own `state.json` duplicates every thread.

- `sh deploy.sh` copies the code to legion, runs the self-check and restarts the service.
- `ssh legion@10.0.0.3 journalctl --user -u devbot -f` follows the log.
- `ssh legion@10.0.0.3 'cd devbot && .venv/bin/python bot.py preview'` prints how each open issue would be sorted without touching Discord.

Keys live in `~/devbot/.env` on legion as `DISCORD_TOKEN`, `OLLAMA_API_KEY` and `GITHUB_TOKEN`, beside `github-app.pem`. devBot acts on GitHub as the devBot-musicastudio GitHub App, installed on every musicastudio repository, so the issues it files and the comments it posts show as devbot-musicastudio[bot]. The app reads and writes code, issues, pull requests and workflows. claudeOpus uses the same app for issue comments and closes, for reviewing pull requests and for merging them outside FSVR, and a plugin in its container refuses James's token for that work. FSVR's main is never changed by claudeOpus: its work goes on a branch named `<GitHub username of whoever asked>/<short description>`, it asks in the thread before opening a pull request, and a person merges it. It makes a token from the app's key each hour. `GITHUB_TOKEN` is James's and is used only to delete an issue, which GitHub keeps for repo admins. Without the key file devBot falls back to that token for everything.

`python sim.py [days]` on legion is a dry run against the live repo and server. It runs the populate, replays the last few days of GitHub activity and files a few sample @devBot reports, printing every thread, post and issue it would create without writing any of them.

`scan.py` sweeps the server's history for bugs and requests the tracker doesn't have yet, skipping #scratchpad, #vop3-ai, #gh-events and the two forums. `fetch` saves the messages, `extract` has the model pull out each report with its message links, and `plan` matches them to issues and groups the rest into proposed new issues in `scan_report.md`. `plan` leaves out every thread a coding agent posts in, since that work reaches devBot as commits. `apply` posts the links into the matching threads and files the new groups, and `attach` copies the files on the quoted messages onto their threads and GitHub issues. Both run only with the service stopped.

`python gate_test.py [model ...]` runs the close confirmation over commit and issue pairs whose answers were checked by hand, and prints wrong closes and missed fixes for each model. Run it after changing the confirmation prompt or the model.

`python history.py` runs the commit check over every commit since the oldest open issue and saves its verdicts to `history.json`. `python history.py apply` closes what that file says was resolved and posts a summary in #devbot, and runs only with the service stopped.

`state.json` on legion maps issues to threads. Deleting it makes the next run populate again and duplicate every thread.
